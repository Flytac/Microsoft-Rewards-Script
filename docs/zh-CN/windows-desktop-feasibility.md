# Windows 中文桌面 App 可行性分析

[返回首页](../../README.md) · 评估日期：2026-10-16

## 结论与范围

**可行，且不必依赖 Docker Desktop。** 仓库已经有 Node 原生入口、Windows 子进程处理和独立控制 API。桌面化主要工作是中文界面、运行环境打包、数据与凭据管理、调度和生命周期管理，并非把 Docker 窗口换一层外观。

这是一份基于当前源码的方案分析，没有创建桌面 App，也没有验证安装包。兼容性和体积需通过原型实测，不能把“理论可打包”当成已发布可运行软件。

## 可直接复用什么

| 当前能力                | 未来用途                         | 要注意的边界                                     |
| ----------------------- | -------------------------------- | ------------------------------------------------ |
| dist/index.js           | 后台任务执行器                   | 入口有 process.exit 与自动启动副作用，应放子进程 |
| scripts/api             | 启停、状态、积分、日志、会话管理 | 历史在内存，重启消失；可选写权限默认关闭         |
| config.json + Validator | 配置表单与校验基础               | 保持键名，中文仅作为显示标签                     |
| manualLogin.js          | 用户交互式登录                   | 需要可见的 Patchright Chromium                   |
| SessionStore            | 登录状态复用                     | SQLite 内含敏感数据，不是加密保险箱              |
| logParser               | 面板结构化数据来源               | 保留原英文输出，中文显示另做映射                 |
| processManager          | 任务生命周期参考                 | Windows 强制终止及浏览器残留需要验收             |

## 两条桌面技术路线

| 路线                        | 优点                                       | 新增成本                                                             |
| --------------------------- | ------------------------------------------ | -------------------------------------------------------------------- |
| Electron + 独立 Node 执行器 | 界面可用 HTML/CSS/TS，适合逐步复用现有技术 | UI Chromium 与自动化 Chromium 通常需分开；更新、资源体积及隔离要设计 |
| Tauri + Node sidecar        | UI 壳与后端进程分工清晰                    | 引入 Rust、sidecar 打包及 WebView2 环境；仍需 Node 和自动化浏览器    |

建议先评估 **Electron 中文界面 + 独立 Node 24 执行器**。这是针对本仓库与初学者学习路径的工程判断，不是已经完成的性能比较。Tauri 的外壳可能更轻，但总安装包仍要计算 Node、Patchright Chromium 与运行依赖，不能只比较空壳体积。

Electron 内置 Node 版本不一定与项目要求、node:sqlite 及 impit 原生模块匹配。使用明确版本的独立 Node 可以减小运行时耦合，代价是多一份运行环境。

## 建议进程边界

中文 UI → 受限的桌面桥接层 → 仅本机控制服务/子进程 → Rewards 执行器 → Patchright Chromium。

初版可复用回环 HTTP API，服务只绑定 127.0.0.1，随机生成本次运行令牌；令牌由可信主进程持有，避免直接暴露任意执行能力给渲染页面。也可后续设计 IPC 适配，但这属于未来重构，应另立任务。

不要把 Microsoft 登录网页加载到具有 Node 权限的界面。Electron 的官方建议包括关闭远程内容的 Node 集成、启用 contextIsolation 和进程沙箱。[Electron 安全说明](https://www.electronjs.org/docs/latest/tutorial/security)

Tauri 支持通过 externalBin 配置 sidecar，但需要匹配目标平台的二进制与调用权限。[Tauri sidecar 文档](https://v2.tauri.app/develop/sidecar/)

## 不依赖 Docker，需要随包解决什么

1. Node 运行时与编译产物 dist，辅助 scripts 与配置模板。
2. 与 Patchright 匹配的 Chromium；不要假定用户安装的 Edge 可直接替代。
3. 运行依赖，包括 impit 等原生模块的 Windows 架构兼容性。
4. 中文字体/编码、含中文和空格的安装路径、非管理员用户启动。
5. 安装目录与数据目录分离：可执行资源只读，用户数据放到合适的用户应用数据目录，并显式设置 cwd/绝对路径。
6. 升级时保留账号配置和 sessions.db，不能无提示覆盖数据。

Patchright 是浏览器控制库，其浏览器安装步骤独立于 TypeScript 编译。[Patchright 项目](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-nodejs)

## 凭据、日志与历史

配置 UI 应隐藏密码/令牌，日志导出默认脱敏。考虑用 Windows 凭据保护能力存放秘密；若运行时仍需 .env，应限制写入范围、访问权限和生命周期。当前代码没有实现这套桌面凭据层，本分析不声称它已有。

Cookie 与 TOTP secret 同样敏感。诊断 HTML/截图可能包含账号信息。不要用自动上传日志作为默认排障方式。

若需要长期积分曲线，新增明确的历史存储层；现有 Control API 只在内存保留有限历史。设计时要区分服务端余额、日志推算增量与任务最终状态。

## 定时、退出与升级风险

Docker cron 不会自动搬到 Windows。需明确选择“App 开着才运行”或“任务计划程序唤醒执行器”；分别测试休眠、断网、错过计划、重复启动与时间变化。

Windows 当前 taskkill /T /F 是强制停止。未来应验证退出时会话一致性、浏览器是否残留、通知是否需要等待，必要时另行实现温和停止协议。本次没有改变其行为。

自动更新需要校验来源、处理运行中升级和失败回滚，不能简单下载覆盖程序。发布包也应保留原作者及 LICENSE，并按适用许可证提供对应源码和 notices；当前只保留既有许可证，不替代正式发布前的许可证核查。

| 5    | 安装包与定时   | 中文路径、普通用户、休眠恢复、卸载保留选项         |
| 6    | 发布           | 签名、更新回滚、许可证与源代码交付                 |
